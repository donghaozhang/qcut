## 修复了什么

### 文本 3DL 不再误走图片解码

12 张 Face AI 候选实际使用标准背景/皮肤双 LUT，shader 与已有 VF 双 LUT 同拓扑，
但纹理源是 `texture/filter_bg.3dl` 和 `texture/filter_skin.3dl` 文本。
原加载器只区分 VF 和 tiled，不能正确处理该格式。

复用已有 `parseAdobeThreeDl`，保留：

- Adobe 索引网格、B 最快变化的行顺序，到 Metal R 最快内存顺序的转换。
- 12-bit LUT 输出精度，不提前量化成 8-bit 图像。
- 原始 cube 大小和两张独立纹理。
- 与 VF 相同的 normalized 3D texture coordinates；不误用 tiled 的半 texel 校正。
- 原包 alpha 权重和分割模型；不是看到两个 LUT 就忽略模型。

加载增加 16 MB 文件尺寸检查，异常网格、缺行、超范围数值和缺失文件明确失败。
单元测试覆盖解析边界、转置、协议采样模式、半透明输入及故障拒绝。

### 不能用包内 Shader 数量推断实际 Pass 数

亮肤、料理、烘培、西餐、法餐包内均有额外 Gaussian blur 资源。
使用仓库现有 serialized-container/value 解析器检查 `main.scene`：

- 只有一台 Camerafilter，输出为 `rt/outputTex.rt`。
- 相机 `layerVisibleMask` 原始值为 `400000000100000000000000`。
- 字段 hash 为 `0x0beb161c`，与 `layerVisibleMask` 的名称 hash 一致。
- 主 filter 在 layer 0；额外 blur mesh 所在 SeekModeScript1 在 layer 3。
- 该字节布局与 64-bit layer bitset、仅 bit 0 开启一致，支持额外 mesh 不参与当前相机输出的判断。

这个判断还结合完整未删减原包的原生 RGBA 对照，而不是移除 blur 后自己对自己测试。
仍只接受固定版本和控制/资源 SHA-256，不推广到同名或未来版本。
亮肤、烘培虽然结构符合，仍因后述灰图误差没有注册。

审计工具同时识别文本 `.3dl` 配对，避免下一轮继续遗漏这种资源。

## 失败与暂缓

| 卡片 | Resource ID | 灰图 RGB MAE / 255 | 最大通道差 |
| --- | --- | ---: | ---: |
| 青提 | `7131290518838938887` | 0.25349418 | 1 |
| 亮肤 | `7127655008715230495` | 0.25032933 | 1 |
| 烘培 | `7127675183246200072` | 0.25774704 | 1 |

三张均通过真实运动帧，返回首帧也逐字节一致；失败发生在切换到全灰 RGBA 的条件。
独立复跑得到相同指标，因此不是仅凭一次瞬态失败撤下。
门禁仍为 MAE <= 0.25、最大通道差 <= 4，不改阈值。

观察到差异主要是同一颜色通道的相邻整数，例如青提大面积原生 R=134、自有 R=135。
这与量化边界或 mask 精度相关，但当前没有证实具体根因，不能直接归结为模型错误，
也不能宣称已经修复或只剩视觉不可见误差。
下一步应对失败灰图固定同一 mask，分别比较浮点 LUT 输出和最终 RGBA8 取整；
再检查原生内部 mask 与读回 mask 的精度差，不用给三个滤镜硬编码颜色偏移。

新增失败帧证据输出：生命周期脚本自动保存 input / metal / native PNG。
失败结果、复跑、候选原始对照均保留在仓库外，未删除失败证据。
单元测试明确断言三张失败 ID 不出现在可选 profiles 中。
