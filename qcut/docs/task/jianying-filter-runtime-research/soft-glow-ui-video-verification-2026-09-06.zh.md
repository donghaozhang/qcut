# 电影柔光：UI 强度、持续帧处理与 QCut 接入验证

日期：2026-09-06。工作分支：`timeline-fixed-prfix`。范围是电影柔光这一条算法链，非剪映整套渲染器。

可读 C++20 实现现在支持独立单帧和持续帧处理；QCut 新卡使用同一实现进行预览和导出。运行算法不加载剪映动态库；精确观感仍需要用户本机的 LUT 数据，源码包不附带该数据。

## 这次确认的算法语义

剪映 UI 的强度不是整条滤镜结果与原图的线性混合。Gaussian 与 SoftLight 保持固定，强度改变 Glow 阈值、亮度和 LUT opacity；最终 Normal 保持固定。

| 强度 t | Glow threshold | Glow brightness | LUT opacity |
| --- | --- | --- | --- |
| 0≤t≤0.8 | `1−0.175t` | `3t` | `0.8t` |
| 0.8<t≤1 | 0.84 | 2.4 | `0.8t` |

80% 与 81% 之间的阈值变化保留原始行为。0% 仍有 SoftLight 底层效果；要看原图，需要关闭滤镜。此定义是可重复的导出快照语义，不宣称完整复刻原生 UI 的实时事件状态机。原生脚本错误、上游 FeatureSegment 的 0 档旁路与 UI 0 档行为分别记录，不能混为一条入口。

正式 C++ 新模式为 `ui-snapshot`。旧的 `output-mix` 仍是独立 CLI 默认值，保留早先六组 CGL 对照的行为；显式传 `--intensity-mode ui-snapshot` 才使用本次 UI 模式。QCut provider 固定使用新模式：`qcut-cpu-soft-glow-ui-snapshot-v1`。

详见 [强度模式定义](../../../research/independent-soft-glow/intensity-modes.zh.md)、[算法契约](../../../research/independent-soft-glow/semantic-contract.zh.md)和[原生事件探针](soft-glow-intensity-probes-2026-09-06.zh.md)。

## 原生 UI 对照如何取得

在本机剪映专业版 11.3.0 创建验证草稿“9月6日”，保留原草稿“8月30日 (3)”。导入自产 1280×720 色卡，添加 5 秒素材；搜索“电影柔光”，点击卡片加号形成正式滤镜轨道，并将滤镜拉长至覆盖整段。通过右侧数字框逐一设置强度，保存设置截图后导出。

独立实现固定绑定缓存 ID `7447126702137904420`、版本 `9673f80b8e2f5a07f02f9ce1130b784a`，验证 scene、PNG 和解码 LUT 三重哈希。UI 这次直接观察到的是同名卡片和实际输出；没有解密当前草稿来单独证明其内部 resource ID/version。UI 和固定包之间的对应还包含目录名称及数值结果的一致性证据。

第一轮 MOV 实际使用 H.264。这些文件保留为历史/顺序对照；随后每档重新打开高级设置，明确选择 Apple ProRes 4444，再以 ffprobe 验证实际编码。最终无滤镜基线及五档参考均为 1280×720、30fps、150 帧 ProRes 4444。共保留 11 张 UI 截图、原始视频、逐帧 SHA、解码命令及 app/library 身份清单。

## 五档数值结果

以零基第 75 帧作固定比较位置。RGB MAE 的单位是 0–255 码值。输入控制分两组保留：原始 PNG 与同一项目导出的无滤镜 ProRes 解码帧；不挑更低的一组替代另一组。

| 强度 | 原 PNG → C++，对 UI 的 RGB MAE | 解码基线 → C++，对 UI 的 RGB MAE | 后者最大通道误差 |
| --- | ---: | ---: | ---: |
| 0 | 0.340657 | 0.106239 | 2 |
| 37 | 0.545537 | 0.380563 | 7 |
| 80 | 0.701910 | 0.553789 | 14 |
| 81 | 0.705149 | 0.555211 | 14 |
| 100 | 0.711324 | 0.565888 | 13 |

所有 Alpha 误差为 0。正式 C++ 与独立候选程序在两种输入、五档输出上均逐字节一致。残差仍包含宿主渲染、颜色转换和 ProRes 编解码，**不能称为像素精确恢复或纯算法误差**。

反例检查：直接用同编码的原图/100 档端点做线性输出混合，37/80/81 档 MAE 分别为 5.135581、3.815345、3.772115；即便将起点改成 UI0，仍分别为 2.062953、3.313383、3.313236。因此仅修改混合起点也不足以解释实际曲线。

H.264 顺序对照中，fresh100 与往返100、80→81 与37→81的第75帧分别完全一致。对应全视频仅121/150、98/150帧同位置逐字节一致，未将中帧一致提升为整片一致。ProRes 基线自身也存在少数变化帧，因此原生导出整片不同 SHA 不直接证明算法有时间状态。

## 真实运动视频与音频

本地人物视频为 854×480、30fps、70帧，其中9种不同图像状态，真实变化集中在末10帧；这不是70个不同运动姿态。新 `ui-snapshot` 37% 模式完整处理70帧约23.02秒，重复处理与乱序 `[69,60,65,61,68,69,0]` 的对应帧均逐字节一致。FFV1 参考无损保存结果；流式处理只保留当前帧及固定中间图像，内存不随视频长度增长。

另一个含音频夹具的封装验证保留了48个 AAC 包的内容哈希、PTS/DTS、duration 和 skip-samples；这是流式接线验证，未把改强度后的重复像素测试误称为重新完成了一套音频编码测试。

当前 CPU 是正确性参考，不能称为实时720p/1080p引擎。产品入口限制为最多1080p像素数、单边最多4096；源码本身的通用图像边界另见契约。透明/HDR/高位深、GPU/SIMD优化及其他操作系统实测仍未完成。

## 产品接入及测试

新卡在 QCut 的独立滤镜库中显示为“电影柔光 · QCut CPU”。预览、Canvas 视频导出和原生帧导出适配共用 C++ helper；会话由模式/尺寸/强度决定，取消和管道失败后终止进程，坏会话不复用。0强度仍经过 CPU，A/B 原图通过关闭效果。旧实验 output-mix 卡要求重新应用，避免悄悄改变已保存描述符含义。

现有工程的`fidelity: native-local`字段仍作为外部帧渲染路径开关复用，独立Metal卡也使用该值；它不等于加载剪映原生库或已经像素对齐。实际实现由明确的CPU provider标识决定，目录`verification`保持`unverified`，UI显示“独立 CPU · 待验证”。

算法、流协议及真实 CLI 测试在 Release 和 ASan/UBSan 下各3项CTest通过；省略模式后的六组旧输出SHA全部保持。产品58项回归通过，Electron和Web生产构建通过。动态库依赖检查中，自产helper只依赖libc++与libSystem。完整产品实现说明见[接入记录](soft-glow-product-integration-2026-09-06.zh.md)。

首轮旧 output-mix 产品E2E已完成应用、100/37预览、强度更新、重开和两次30帧视频导出，原生fallback请求为0；这份历史接线证据不代替最终UI模式的E2E结果。

新模式第二轮 E2E 发现实际预览缺陷：0 档切换 A/B 后快速改到 37，状态和成功 IPC 均已更新，画布却停在 0。受控慢帧测试复现了原因：不同 React effect 各自启动请求占满队列，最新请求失败，旧请求成功后又被 cleanup 取消提交。现在以组件持久队列串行调度，取消的任务在启动前跳过；测试中实际只执行 0→10→37，并发峰值为 1，最终画布和 marker 都为 37。卸载也不会启动已取消的排队任务。相关组件、预览和导出路由共 26 项测试及前端类型检查通过，随后 Web 生产构建通过。失败的 run2 证据保留，最终复跑继续使用原来的快速强度切换序列。

最终 **run4：1 项真实 Electron E2E 通过，用时约 1.3 分钟**。共 76 次实际 CPU 响应：100 预览 3、100 导出 30、0 预览 3、A/B 恢复 0 预览 3、快速强度切换及 37 预览 7、37 导出 30。正常流程 IPC failures、原生 fallback 请求和页面错误均为 0。

- 100、0、恢复后的 0 三个暂停状态，480×270 画布的实际 RGBA SHA-256 与相应 CPU 返回值相等；0 输出确实不同于原图。A 显示原图，B 恢复原来的 0 强度。
- 保留快速 0→10→20→30→40→39→38→37 输入序列，最终画布 marker 更新到 37，画面截图变化。项目 URL 完整重载后，描述符仍为新 provider、37 强度；公共导航 helper 在跳转前等待 networkidle 超时，随后以显式 `page.goto(projectUrl)` 重载验证持久化，因此没有将它表述为成功经过项目列表离开再打开。
- 100 和 37 两支导出均实际生成 1280×720、30fps、30 帧、1 秒 H.264 文件。两支视频的零基 0/15/29 帧各自有不同像素哈希，确认包含运动。编码结果不作无损逐字节对齐声明。
- 注入 CPU 失败时，预览明确显示失败，导出拒绝且未产生输出文件，未调用原生 fallback。

run3 曾因抽取测试 helper 时遗漏 `paused` 局部变量提前失败，修正测试声明并通过单文件类型/格式检查后进入 run4；它与 run2 的产品队列缺陷分别保留。最终证据为同级 `e2e/run4/editor-evidence.json`，历史失败目录未删除。
