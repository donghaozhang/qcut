# QCut 美颜美体与中文剪映专业版差距审计

记录时间：2026-08-25

## 审计口径

本文在完成中文剪映专业版独立研究后，才检查 QCut 当前分支。剪映侧基线来自
本机中文剪映专业版的 UI、资源目录、效果包和运行时审计。

本文把结果分成四种状态：

- **已覆盖**：QCut 有产品 UI、参数持久化和本机原生渲染链路，并有当前测试证据；
- **部分覆盖**：核心路径能运行，但目录规模、离线性、生命周期或交互仍不完整；
- **缺失**：剪映有独立产品链路，QCut 当前没有对应实现；
- **未证明平价**：QCut 有效果输出，但没有与同版本剪映 UI 对同一无损素材逐像素对照。

“滑杆存在”“原生宿主返回成功”“截图看起来有变化”和“与剪映相同”是四件不同的事。
本文不会把前三者当成像素平价证明。

## 结论先行

QCut 已经覆盖剪映的主要**自动**人像链路：人脸识别、逐脸选择、皮肤、脸型、五官、
美妆、整帧美体、自定义预设、预览、导出以及 CLI 状态写入都已接入本机 Swing 运行时。
它不是一套假控件，也不是 CSS 或 Canvas 近似美颜。

但 QCut 还不能称为“完整复刻剪映美颜美体”，主要差距依次是：

1. **手动美颜和手动美体完全缺失**：没有画笔、橡皮擦、局部区域、算法缓存、撤销/重做，
   也没有拉长、局部瘦身瘦腿、放大缩小三种交互工具；
2. **官方卡片和预设目录尚未产品化**：当前剪映美妆目录的 151 张效果包已进入 QCut 私有快照，
   但产品仍只展示静态登记的 15 张，没有动态解析完整目录、封面、参数和在线状态；
3. **跨会话人物身份没有证明**：当前能在一次检测和后续各效果包之间做 track id 重映射，
   但重新打开项目后仍不能保证“人物 1”是同一个现实人物；
4. **绝大多数单项没有逐卡像素平价**：已证明真实生效，不等于已证明与剪映 UI 无损输出一致。

## QCut 当前实现

### 产品调用链

```text
QCut 属性面板
  -> MediaPortraitAdjustments
  -> 预览帧 / 导出帧
  -> jianying-portrait-adjustment IPC
  -> createJianyingPortraitAdjustmentProvider
  -> 按效果包生成顺序 stage
  -> 每个 stage 的长生命周期本机宿主
  -> FeatureSegment 参数 + Swing 原生运行时
  -> 当前 stage RGBA 输出作为下一 stage 输入
  -> 最终预览或视频导出
```

当前 stage 顺序为皮肤、眼部、肤色、牙齿、脸型、五官、美妆和美体相关包的固定顺序。
同一个效果包会复用宿主会话；素材、尺寸或时间线发生不连续时会退役旧会话，避免 tracker 和
算法缓存污染下一素材。

### 当前能力清单

当前合同目录共有 **77 个数值控件**：

| 分组 | 数量 | 内容 |
| --- | ---: | --- |
| 皮肤 | 8 | 磨皮、美白、清晰、匀肤、丰盈、祛斑祛痘、肤色、冷暖 |
| 脸型 | 17 | 瘦脸、窄脸、V 脸、下颌、颧骨、下巴、发际线等 |
| 五官 | 42 | 眼、鼻、嘴、眉、眼部细节、白牙和补充脸型参数 |
| 美体 | 10 | 小头、天鹅颈、瘦手臂、直角肩、宽肩、瘦身、瘦腰、长腿、胸型、美胯 |

其中人脸相关 67 个，美体 10 个。运行时解析 12 个聚合包：

```text
smooth, whiten, clarity, spot-acne, skin-gan, eye-details,
skin-tone, teeth, face, features, makeup, body
```

产品美妆目录当前展示 **15 张卡、12 个分类**，覆盖整妆、口红、腮红、修容、卧蚕、眉毛、
睫毛、眼线、眼影、美瞳、高光和雀斑。QCut 私有快照同时保存了当前剪映目录响应中的
**12 类、151 张卡元数据和 151/151 个效果包**，另保留一张兼容旧卡“流畅眉”。这批资源尚未
接入动态产品目录，所以“本机已缓存”不等于“UI 已支持”。

### UI 已有能力

QCut 当前属性面板已有：

- 美颜、美体、美颜预设、美体预设四个顶层页；
- 皮肤、脸型、五官、美妆四个美颜子页；
- 原生运行时状态、启用开关和刷新；
- 当前帧人脸识别、人脸框、单人选择和多人检测；
- 按人物保存数值参数和美妆卡；
- 明确显示自动美体作用范围为“全部人物”；
- 参数分组重置和全局重置；
- 自定义预设保存、应用、删除、重命名、覆盖、缩略图、JSON 导入和导出。

皮肤页顶部仍保留 QCut 既有的“补光”和通用“美颜”增强控件。它们不属于剪映原生
效果包链路，和下方原生皮肤参数混排会造成语义歧义，后续 UI 应明确分组或改名。

### 多人参数怎样工作

QCut 保存一个全局兼容层和可选的 `faces[]` 逐人层。每个人使用当前原生检测返回的
`trackId` 保存数值参数和美妆选择。由于每个效果包拥有独立 tracker，provider 会先在该包内
检测，再按人脸几何把 UI 检测 ID 映射到该包 ID，最后重写 FeatureSegment 参数。

这个设计解决了“同一帧不同包从 0 重新编号”的问题。它没有解决跨会话生物身份：track id
仍是运行时短生命周期 ID，不是持久人物档案。剪映本身依赖 `freid` 和素材生命周期；QCut 若要
让预设长期绑定同一演员，还需要持久人物身份层或重新打开后的可靠匹配协议。

### 美体语义

QCut UI 把自动美体固定为“全部人物”，这与当前剪映 body 聚合包一致。该包只读取参数向量
第一项强度，不读取人物 id，所以逐脸保存美体值会产生错误预期。QCut 已在 stage 构建时把
美体塌缩为整帧单条目。

QCut 没有单独暴露“瘦腿”。虽然原生枚举和包配置能看到 `SlimLeg`，当前官方聚合包 Lua
没有映射它，直接发送参数会被忽略。剪映可见的“瘦身瘦腿”属于手动美体的另一条链路，
不能拿自动“瘦身”滑杆代替。

### CLI 能力

当前 CLI 不是另起一套人像渲染器。它通过编辑器桥的 `editor:element:patch` 写入素材元素的
`portraitAdjustments`，随后与 UI 共用同一个预览、原生 provider 和导出链路。因此 CLI 写入后
应在属性面板可见，导出也应消费同一状态。

这条链路已验证逐脸参数、美妆和整帧美体状态写入；当前没有单独的手动画笔 CLI 协议。

## 当前本机运行状态

2026-08-25 对当前 provider 实时调用 `inspect()` 得到：

```text
state: ready
available: true
offlineReady: true
catalog: 77
makeup cards: 15 / 15 ready
```

12 个聚合包和当前产品的 15 张美妆卡均来自 QCut 私有快照：

```text
smooth, whiten, clarity, spot-acne, skin-gan, eye-details,
skin-tone, teeth, face, features, makeup, body
```

当前内容寻址快照为
`D6342ECD-5432-33F0-A2AD-0C28F5699994-7ba834f1491b9bd2`，清单包含 34,428 个文件、
892 个包版本和 1,481,061,427 bytes。当前 `rp.db` 美妆目录快照包含 12 类 151 张卡，
151/151 个对应效果包均在清单中。完整性检查无缺失，也没有遗留 staging 目录。

该结果表示执行时可以同时禁用剪映 App Bundle 和剪映用户模型缓存；首次创建或刷新快照仍要求
用户本机已有且有权使用来源资源。私有快照只能作为用户本机、不可上传的互操作资产处理，不能随
仓库或发行包分发。

## 当前真实 E2E 证据

本轮用现有真人素材执行：

```bash

QCUT_REAL_PORTRAIT_IMAGE_PATH="$HOME/Downloads/ChatGPT Image Jul 27, 2026, 03_11_53 PM.png" \
QCUT_REAL_MULTIFACE_IMAGE_PATH=/tmp/qcut-portrait-real-two-face/input-1024x512.png \
bunx playwright test apps/web/src/test/e2e/jianying-portrait-adjustment.e2e.ts
```

结果为 **2 passed，59.6 秒**。证据目录：

```text
output/playwright/jianying-portrait-adjustment/
```

已证明：

- 皮肤、脸型、五官、美妆和美体各 stage 都产生不同 RGBA 哈希；
- 两人画面真实检测到两张脸并显示人脸框；
- 只给左侧人物应用口红后，左侧改变 `2515` 像素，右侧改变 `0` 像素；
- 美体页明确显示“全部人物”；
- CLI patch 在 `120 ms` 返回成功，逐脸瘦脸、逐脸口红、瘦腰和长腿状态回显到 UI；
- 真实导出得到 1 秒、30 帧、1080x1920 的 H.264 MP4，大小 `233813` bytes。


这些证据证明功能链路和逐脸局部性，不证明每个卡片与剪映 UI 逐像素一致。截图文件名本身不是

### 严格离线人像包门禁

补齐 `whiten`、`clarity`、`spot-acne` 和 `skin-gan` 后，同时设置
`QCUT_JIANYING_DISABLE_APP_BUNDLE=1` 与 `QCUT_JIANYING_DISABLE_USER_CACHE=1`，再对两张真人素材
执行极值渲染。四份报告均记录 `offlineReady=true` 且 12/12 包来源为 `qcut-private`：

- 美白分别改变 125,603 和 32,819 个像素；
- 清晰分别改变 187,538 和 118,719 个像素；
- 祛斑祛痘执行两张素材乘三次独立冷启动，6/6 次均为 `functional`，没有透传；
- 匀肤分别改变 50,828 和 20,243 个像素，丰盈分别改变 88,455 和 33,545 个像素。

结构化报告与对比图位于仓库忽略目录：

```text
output/playwright/jianying-portrait-offline-audit/
```

聚焦回归使用仓库正式 Vitest 配置运行人像合同、stage 顺序、逐脸 scope、跨包 track id
重映射、时间线连续性、预览 source key 和 CLI bridge：**6 个测试文件、35 项全部通过**。
这些单测验证状态和协议；真人像素输出仍以上述 Playwright E2E 为准。

## 仍需完成的工作

### P0：补齐剪映真正独立的交互链路

1. 研究并实现手动美颜的画笔/橡皮擦、大小、强度、脸框约束、算法缓存、重置与撤销/重做；
2. 研究并实现手动美体的拉长区域、局部瘦身瘦腿、放大缩小和可视化控制柄；
3. 为上述两条链路建立项目持久化、预览、导出和 CLI 协议。

这不是增加几个 slider；需要新的交互数据模型、画布工具、原生调用协议和时间线状态。

### P1：收紧当前自动链路

1. 从私有 `rp.db` 动态生成 151 张美妆目录，通用解析缩略图、参数键、默认强度和效果包结构，
   对尚未验证的结构保持禁用而不是静默近似；
2. 继续对祛斑祛痘做连续帧压力测试。当前两张素材的 6 次独立冷启动已全部通过，但仍不能替代
   长视频连续帧门禁；
3. 用真实多人运动短视频验证遮挡、人物进出、时间回跳、素材切换和重新打开项目；
4. 把通用“补光/美颜”和原生剪映皮肤控件在 UI 中明确分层。

### P2：建立平价矩阵

对每个拟发布控件固定以下四方证据：

```text
原始无损帧
中文剪映专业版同参数导出
QCut 原生预览
QCut 原生导出
```

分别记录全帧、脸部 ROI、mask 边缘、背景、重复帧和编码前无损帧指标。只有通过门禁的项目才标
`verified`；仅有非零差分的项目标为 `functional`，视觉接近但未达门禁的项目标为 `close`。

## 最终判断

按“自动美颜美体能否在 QCut 中真实使用”衡量，当前主链路已经可用；按“是否完整复刻剪映”衡量，
当前仍是**部分完成**。最大的产品缺口不是再加一批自动滑杆，而是手动精修/手动美体、完整动态
美妆目录、长期人物身份和逐卡平价证据。

本轮只提交研究文字。剪映二进制、模型、效果包、缓存数据库和原始素材均未加入仓库。
