# 剪映 CV 特效解锁可行性(matting / face / skeleton)

日期:2026-08-17 · 分支:effects-v2 · 状态:**调研完成,结论为"未证实可行"**

参照生产线([jianying-effect-reference-line](../jianying-effect-reference-line/README.md))
把 618 个 blit-only 特效全部拿到了参照。本文调研剩下的 **406 个 CV 特效**
能不能解锁——它们需要剪映的算法能力(抠像、人脸关键点、骨骼等),目前在
目录里标 `supported: false`,实验室 UI 显示「需剪映算法」。

## 一句话结论

**不是"一个补丁的距离"。** 挡在前面的是**两道独立的墙**:第一道已被实验
证明可拆(接上模型解析回调,算法子系统真的活了、模型真的加载了);第二道
在此之前**没有任何人发现**——算法图始终收不到输入图像,即便模型全部正确
绑定,渲染结果仍与输入**逐字节相同**。在有人做出第一个"真正变了画面且跟随
主体"的渲染之前,这 406 个的状态是 **UNPROVEN,而不是"快好了"**。

## 一、这 406 个到底是什么

数据直接从剪映的 sqlite 目录缓存统计,两个独立 agent 各自复现,数字一致。

| | 画面特效 effects2 | 人物特效 face-prop | 合计 |
|---|---|---|---|
| blit-only(已全部拿到参照) | 591 | 27 | **618** |
| CV 门禁 | 116 | 290 | **406** |
| 小计 | 707 | 317 | 1024 |

**人物特效 91.5% 都在 CV 门后**,画面特效只有 16.4%。这也解释了为什么参照
库里人物特效只有 27 条。

**能力分布**(一个特效可能要多项,29 种非 blit 能力):
`face` 243、`matting` 188、`skeleton` 57、`ext_texture_producer` 25、
`expression_detect` ~19、`face_fitting` 16、`avatar_drive` 13、`skin_seg` 12,
其余 21 种都是个位数长尾。

**累计解锁曲线**(必须覆盖某特效**全部**缺失能力才算解锁):

- 只解决 `face` → 124 / 406(30.5%)
- 再加 `matting` → 256(63.1%)
- 再加 `skeleton` → **309(76.1%)**
- 要拿满 406,得把 29 种能力全做完

245 个特效只缺**一项**能力(face 124、matting 100、skeleton 12…),另 161 个
缺两项以上。

**素材可得性不是瓶颈**:406 个**全部**有可下载的签名包地址;模型权重也大多
在本机——用户的剪映缓存里有 53 个 `.model`(168MB),应用包里另有 72 个
(202MB),**315/406 的特效所需模型已全部在本地**。

## 二、CV 包的工作机制

CV 包和普通包**结构上几乎一样**,差别只有两点:

1. 一份更复杂的 `algorithmConfig.json`——一张算法节点图,节点名和目录里的
   能力词表一一对应(`face_0`、`matting_0`、`skeleton_0`、`blit_0`、
   `extTextureProducer`…)。**这份文件才是每个包真正的能力声明**。
2. 素材/脚本消费算法结果的方式:材质采样引擎自有的共享纹理
   (`share://bgmask.texture`、`share://depth.texture`、
   `share://skinsegmask.texture`),或 Lua 里读算法结果 API。

**包里不含任何模型权重**——只用符号名(`tt_matting`、`tt_face`、
`tt_face_extra`、`tt_skeleton`…)引用,**由宿主负责解析成本地文件路径**。
这就是关键接口:创建 SwingManager 时可以传一个**资源查找回调**,运行时通过
它索要模型。

QCut 的滤镜通路**早就实现并在用**这套回调(`filter-probe.mm` 传
`findModelResource` + `ModelCatalog`),而特效通路在同一个参数位上传了
`nullptr`([effect-probe.mm](../../../research/jianying-runtime-probe/effect-probe.mm) 约 :283)。
所以门禁不只是 TypeScript 里的白名单——**原生宿主根本没有加载模型的能力**。

## 三、决定性实验(已执行)

把 probe 源码复制到临时目录(**仓库未被修改**),按上述思路补上资源查找
回调与模型目录,用仓库自己的编译命令重编,渲染真实 CV 包。

### 第一道墙:模型解析缺失 —— 真实存在,且可拆除 ✅

| | 基线(finder=null) | 接上 finder+目录 |
|---|---|---|
| `initAlgorithm: finder is null` | 1 次 | **0** |
| `updateAlgorithm: managers are nullptr` | 每帧 | **0** |
| AlgorithmService 实例 | 无 | **创建成功** |
| 模型加载成功 | 0 | **2** |
| `AlgorithmMatting _doInit` | 未触发 | **触发** |

算法子系统确实活了。六份报告都猜这一步能成,实验确认了。

### 第二道墙:算法收不到输入图像 —— 新发现,未解决 ❌

**即便模型全部正确绑定,输出仍与输入逐字节相同(12 帧 0 帧变化)。**
运行时报:

- `AlgorithmMatting input buffer is null`(11/12 帧)
- `AlgorithmTextureBlitter input param invalid`(11/12 帧)
- 一次性的 `BachAlgorithmTextureBlitter getSrcImage blitterManager is invalid`

算法图**从头到尾没拿到输入图像**。这是一道与第一道完全独立、成因未知的墙。

**因此"接上 finder 就能跑 matting"是错的**,报告里"约 20–40 行原生 diff"
的估算也不成立——那个 diff 已经被实现了,产出仍是恒等。

## 四、实验中挖出的坑(每一条都能坑掉几小时)

- **错模型会产生"看起来成功"的假象**。现有 `ModelCatalog` 只有三条家族
  规则、按前缀字母序回退,对真实模型目录会**绑错模型**
  (`tt_face` → 年龄属性模型;`tt_matting_v15.0` → 另一个 matting 变体)。
  更危险的是:**错模型那次跑出了 5.59% 的画面变化**(首帧变了、看着像生效),
  而**正确模型那次是 0.00%**。只看"画面变没变"的验收会直接得出错误结论。
- **回调返回 nullptr 会段错误**(exit 139),死在图形初始化阶段。生产实现
  必须保证任何请求都返回有效路径。
- **模型请求键的格式**:运行时按 `/<子目录>/<带版本文件名>` 索要
  (如 `/ttfacemodel/tt_face.model`、`/mattingmodel/tt_matting_v15.0.model`),
  这对应**应用包里的模型树布局**,而不是用户下载缓存的扁平命名。而且运行时
  索要的版本号**磁盘上并不存在**(要 v11.1,盘上是 v11.2),所以**必须做
  版本容忍的词干匹配**,精确匹配一定失败。
- **`no GL context` 警告是无辜的**。它在"失败"和"模型加载成功"两次运行里
  **同样出现一次**,不构成因果。之前有报告把它当成唯一阻塞点,是错的。
- **`撕纸特写` 是"看起来在动其实 CV 没参与"的典型**:它确实渲出可见变化,
  但**接不接模型输出完全一致**(逐字节相同)——可见部分全部来自非 CV 子特效。
- **异步开关无效**:把 SwingManager 的 algorithmAsync 打开,结果完全不变。

## 五、被证伪的判断

调研过程中两个流传的说法被实验推翻,记录在此以免重犯:

1. **"运行时没有外部结果注入 API"——错**。逐个符号核验,
   `bef_swing_manager_set_resource_finder`、
   `bef_swing_segment_video_set_algorithm_buffer`、
   `bef_swing_segment_video_algorithm_init/_need_run/_excute`、
   `bef_effect_mv_set_external_algorithm_result_image`、
   `bef_algorithms_pure_execute_algorithm_by_name` 等**全部存在**。
   之前的否定结论是把搜索范围限定在"QCut 已经绑定的符号"之后,又把结果
   当成了运行时的属性。这是整组调研里最危险的一个错误,因为它会直接封死
   一整条可行路线。
2. **"GL 上下文缺失是唯一阻塞"——错**(见上)。

运行时的 CV API 面其实相当完整:模型加载 / 推理 / 读结果的 C 接口齐全,
推理库和人脸 SDK 都已在 QCut 打开的那个闭包里。**能力可用性不是瓶颈,
输入管线才是。**

## 六、下一步(按性价比排序,都是小实验)

针对第二道墙,有三发独立的、便宜的子弹,任何一发命中都会翻转结论:

1. **原生纹理上传标志**(约 10 行,**最高价值**)。特效通路的每帧请求把
   `nativeTextureFlags` 留成了默认全 false,而滤镜通路用的是 CVPixelBuffer
   背书的原生缓冲(probe 里已有对应环境变量,默认 `{0,0,1}`)。也就是说
   特效通路用普通 2D 纹理上传输入——这正好能解释"算法输入缓冲为空"。
   成功信号:`input buffer is null` 归零。
2. **显式驱动每段算法**:`bef_swing_segment_video_algorithm_init` →
   `_need_run` → `_excute`,这三个导出符号 QCut **一个都没调**,而命名强烈
   暗示宿主需要自己驱动。签名未知,要在崩溃隔离的子进程里试。
3. **走扁平 EffectSDK 通路**:`bef_effect_init` 直接吃**模型目录**(不需要
   回调),`bef_effect_algorithm_texture` 每帧显式喂算法。仓库里已经有这个
   宿主(滤镜本地桥接),**零新增原生代码**就能试,而且测的是一条完全不同
   的输入路径。

另有一个必须先消掉的**混淆变量**:上述实验的输入是合成图形,不是真人。
face 包那次**没有报输入错误**却仍是恒等——这既可能是"人脸通路坏了",也
可能只是"画面里没有人脸"。**用真人素材重跑一遍**是眼下最便宜的决定性实验。

## 七、顺带发现的两个既有 Bug(与 CV 无关,建议单独修)

调研过程中发现**已上线的工作里有两处正确性问题**:

1. **门禁读错了字段**。当前用目录的 `requirements` 数组判定,但 618 个
   "blit-only" 里有 507 个的 `requirements` 是**空数组**——是靠"空即通过"
   混过去的。按包内 `algorithmConfig.json` 的真实节点图复查,**19 个已被
   判定为 supported 的包实际声明了 CV 节点**(face 17、nh_face_align 16、
   expression_detect 6、matting 2、skeleton 1、avatar_drive 1、depth 1),
   而且不限于人脸那一簇。**门禁应改为读 algorithmConfig.json。**
2. **参照库里有 34 条重复片**。按 sha256 比对,618 条参照中有三组逐字节
   相同(16 + 16 + 2 条),**全部标着 ok=true**;现有的 SSIM > 0.997 恒等
   标记一条都没抓到。批渲验收需要补:跨片 sha256 碰撞检测 + 逐片时间方差
   检查。

## 八、战略结论

即使第二道墙被攻破,这条路的天花板依然是:**仅 macOS、依赖用户本机装了
剪映、且一个模型权重都不能分发**。而且当前**随产品分发的桥接二进制根本
不支持 effect 模式**(只有开发编译的那份支持),真要上还得解决桥接的重编
与分发。

所以**现实收益是"更多参照片供 Gen-1 自研复刻",而不是"多 406 个可用特效"**。
考虑到 QCut 自己已经有 MediaPipe 人像抠像(且已接入预览与导出),
**那 100 个只需 matting 的特效,很可能不解锁运行时也能自研复刻**——这条
路反而更划算。

**建议**:把第六节那三个实验作为**限时 spike**(便宜、独立、任一命中即
翻转结论)去跑;在拿到第一个"画面真变了且跟随主体"的渲染之前,**不要**
按"CV 解锁计划"投入。第七节那两个 Bug 与本决策无关,建议现在就修。

## 附:QCut 自有 CV 能力现状

- **有**:MediaPipe 人像分割(`selfie_multiclass_256x256`,float32 tflite,
  CPU delegate),输出 0..1 的单通道 `Float32Array` 覆盖度掩码,跑在渲染进程
  的 Web Worker 里。
- **没有**:人脸关键点 / 姿态 / 手部——代码里零实现(打包的 vision 运行时
  虽然导出了对应类,但权重和调用代码都缺)。
- **注意**:CLI 的 `person-cutout` 是**云端** fal.ai 抠像往返,**不是本地
  模型**,所以 QCut 目前**没有无头本地抠像能力**——而桥接是独立二进制,
  需要的正是无头能力。
- 字节层面兼容性其实不错(两边都是直通 alpha、全范围 sRGB、顶行优先
  RGBA8),真正缺的是**注入口**。
- 量级上限:替代 matting 最多覆盖 406 中的 **100** 个;243 个要 `face`,
  QCut 完全提供不了。
